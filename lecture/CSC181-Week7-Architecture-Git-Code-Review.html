Software architecture

What is software architecture?

Definition

The set of structures needed to reason about a system: its elements, the relations among them, and the properties of both.

1

Elements

Components, services, modules, databases

2

Relationships

Who calls whom, what data flows where, what depends on what

3

Decisions and rationale

Why it is this way, and what alternatives were rejected

Architecture is the decisions that are hard to change. Choosing a database is architecture; choosing a variable name is not.

L. Bass, P. Clements & R. Kazman, Software Architecture in Practice, 4th ed. (2021)

08

Architecture styles

Start with a modular monolith

Modular monolith

  • One codebase, one deployment
  • Clear modules inside: events, auth, notifications
  • Easy to run, test, and debug on a laptop
  • Can be split later if a module needs to scale

Microservices

  • Many services, many deployments
  • Network calls instead of function calls
  • Needs containers, monitoring, and service discovery
  • Pays off with many teams and heavy scale

For a 12-week, 4-person project, choose the monolith. Microservices solve organizational problems you do not have.

M. Fowler, "MonolithFirst" (2015)

Software architecture

Record decisions as ADRs

docs/adr/002-cached-schedule.md

# ADR-002: Cache the schedule; show "last updated"

Status: Accepted (Week 7)

Context: Visitors have weak signal at venues.
Real-time sync needs a constant connection.

Decision: Cache the schedule on the device.
Label every event with its last update time.

Consequences: Works offline. Data can be up to
15 minutes old. Notify savers of changes.

Short

One page per decision. Context, decision, consequences.

Kept in the repository

docs/adr/, numbered, reviewed in pull requests like code.

Never deleted

If a decision changes, write a new ADR that supersedes the old one.

Defense evidence

Answers "why did you do it this way?" months later.

M. Nygard, "Documenting Architecture Decisions" (2011)

Modularity

Cohesion and coupling

High cohesion: good

Everything in a module serves one purpose.

events/ holds event rules, validation, and queries. Nothing about passwords.

Low coupling: good

Modules depend on each other as little as possible, through small interfaces.

The notifier gets "event 12 changed"; it does not read the events table directly.

The test: how many files must change to make one small change? If the answer is "many, in many folders", coupling is too high.

Recall Week 2: the time-format bug that needed the same fix in three places was a cohesion and duplication problem.

D. Parnas (1972) · W. Stevens, G. Myers & L. Constantine, "Structured Design" (1974)

13

Design principles

Six principles you will use every week

1

Separation of concerns

Different jobs in different places: UI, rules, data

2

Single responsibility

A module or function has one reason to change

3

Information hiding

Hide decisions likely to change behind an interface

4

DRY

Don't Repeat Yourself: one source for each piece of knowledge

5

KISS

Keep it simple: the simplest design that meets the need

6

YAGNI

You Aren't Gonna Need It: do not build for imagined futures

Principles are guides, not laws. Two similar lines are not always duplication; a little repetition beats the wrong abstraction.

Git workflows

Git in one picture

1

Working directory

You edit files

2

Staging area

git add: choose what goes in

3

Local repository

git commit: save a snapshot

4

Remote (GitHub)

git push: share it

git pull brings teammates' commits back down. Pull before you start; push when a piece of work is ready.

A commit is a snapshot

With an author, a time, a message, and a parent. That is your contribution record.

A branch is a pointer

A movable label on a line of commits. Cheap to create, cheap to delete.

main is shared

Always working, always deployable. Never commit straight to it.

S. Chacon & B. Straub, Pro Git, 2nd ed. (git-scm.com/book)

Git workflows

Merge conflicts: normal, fixable, preventable

What a conflict looks like

<<<<<<< HEAD
const RADIUS_KM = 1;
=======
const RADIUS_KM = 0.5;
>>>>>>> 31-smaller-radius

// after talking it through: keep 1 km,
// make it a setting for organizers
const RADIUS_KM = config.nearMeRadiusKm ?? 1;

Why it happens

Two branches changed the same lines differently. Git cannot guess which is right.

How to resolve

Talk to the other author, edit to the correct version, delete the markers, run tests, commit.

How to prevent

Small branches, merged in days; pull main often; split big files by responsibility.

A conflict is a conversation, not an error. The right answer is a decision, sometimes neither version.

Pull requests and code review

Anatomy of a good pull request

Add near-me filter to event list #34

open12-near-me-now → main · 4 commits · 3 files

What: Lists events within 1 km starting in the next 60 minutes. Closes #12.

How: New nearNow() in the events service; list view calls it.

Tested: unit tests for 0, 1, and 5 events; checked on a phone with location off.

Screenshots: list, empty state, location denied.

Reviewer: @cara · Checks: lint ✓ tests ✓

@cara commented on events/service.js

What happens if an event has no end time? Could we add a test for that case?

@ana replied

Good catch: it was skipped. Fixed in the latest commit, with a test.

Small

Ideally under about 400 changed lines. Big PRs get skimmed, not reviewed.

Linked

"Closes #12" ties the code to the story and its acceptance criteria.

Self-reviewed

Read your own diff first; remove debug code and stray files.

Templated

A pull_request_template.md prompts what, how, tested, screenshots.

Pull requests and code review

Why review code, and what to look for

Why review

  • Catch defects early, when they are cheap
  • Share knowledge: no part known by only one person
  • Keep the codebase consistent
  • Mentor and learn from each other

What reviewers check

  • Does it meet the story's acceptance criteria?
  • Is it correct, including edge cases and errors?
  • Is it readable: names, structure, comments where needed?
  • Are there tests? Any secrets or debug code?
  • Does it respect the architecture and layers?

Approve when the change makes the codebase better, even if it is not exactly how you would have written it.

Google Engineering Practices: Code Review Developer Guide (google.github.io/eng-practices)

Reviewers

Pull requests and code review

Protect main with rules and automation

Branch protection

No direct pushes to main; changes arrive only through pull requests

Required review

At least one approving review from a teammate before merging

Required checks

Lint and tests must pass in CI before the merge button turns green

GitHub Actions

A short workflow file runs your checks on every push and pull request

PR template

Prompts for what, how, tested, screenshots, linked issue

CODEOWNERS (optional)

Automatically requests review from whoever owns a folder

Set these up this week, before Sprint 1. Adding rules later always feels like a punishment.

Sprint 1 plan

Your contribution is visible in the repository

What counts as evidence

  • Commits with clear messages
  • Pull requests you opened, linked to issues
  • Reviews you gave, with real comments
  • Issues you created, refined, or closed
  • Docs, diagrams, tests, and ADRs you wrote

What undermines it

  • Committing a teammate's work under your name
  • Rewriting history to change authorship
  • Giant last-minute commits of everything
  • Approving PRs you did not read
  • Work done outside the repository and never pushed

Pair programming? Add a Co-authored-by: line to the commit so both people get credit.
