05

Quality assurance

Error, defect, failure

1

Error (mistake)

A person writes h % 12 and forgets that 12 % 12 is 0

2

Defect (fault, bug)

The wrong line sits in formatTime in the repository

3

Failure

A visitor sees "0:00 PM" for the noon parade

Not every defect fails

A defect in code no one runs stays hidden until someone does.

Testing finds failures

Debugging then finds the defect that caused them.

Reviews find defects directly

Without running anything. That is why code review is QA.

06

Quality assurance

Seven principles of testing

PrincipleIn practice
1. Testing shows the presence of defects, not their absencePassing tests raise confidence; they do not prove correctness
2. Exhaustive testing is impossibleChoose tests with techniques and risk, not at random
3. Early testing saves time and moneyTest the requirements and design, then each story as it is built
4. Defects cluster togetherMost bugs hide in a few modules: dates, money, permissions
5. Tests wear outThe same tests stop finding new bugs; add and vary them
6. Testing is context dependentA festival guide and a payment app need different rigour
7. "No bugs" does not mean usefulA defect-free app that solves the wrong problem still fails

Testing levels

The test pyramid

Many unit tests

Milliseconds each. Run on every save. Pinpoint the broken function.

Some integration tests

Check the contracts between parts: the API, the database, the queries.

A few end-to-end tests

Only the critical journeys: view today's events, organizer edits one.

Plus exploratory testing

A person trying to break it. Finds what no one thought to automate.

M. Cohn, Succeeding with Agile (2009) · M. Fowler, "TestPyramid" (2012)

09

Testing levels · example

A unit test: arrange, act, assert

lib/time.test.js

import { formatTime } from './time';

test('noon shows as 12:00 PM', () => {
  // Arrange
  const noon = new Date('2026-10-20T12:00:00+08:00');
  // Act
  const label = formatTime(noon);
  // Assert
  expect(label).toBe('12:00 PM');
});

test('midnight shows as 12:00 AM', () => {
  const midnight = new Date('2026-10-20T00:00:00+08:00');
  expect(formatTime(midnight)).toBe('12:00 AM');
});

One behaviour per test

The name says what should happen. A failure tells you exactly what broke.

Test the edges

Noon and midnight are where the Week 2 bug lived.

Fast and independent

No network, no shared state, any order.

Fix the time zone

Run tests with TZ=Asia/Manila so CI matches your laptop.

An integration test: API and database together

tests/events.api.test.js

import request from 'supertest';
import app from '../src/api/app';
import { resetDb, seed } from './helpers';

beforeEach(resetDb);

test('lists only that day, sorted by time', async () => {
  await seed([
    { title: 'B', start: '2026-10-20T19:00+08:00' },
    { title: 'A', start: '2026-10-20T18:00+08:00' },
    { title: 'X', start: '2026-10-21T18:00+08:00' },
  ]);
  const res = await request(app).get('/events?date=2026-10-20');
  expect(res.status).toBe(200);
  expect(res.body.map(e => e.title)).toEqual(['A', 'B']);
});

Real parts, test data

A test database, reset before each test, so results repeat.

Checks the contract

Status code and shape from the Week 8 API example.

Covers two criteria at once

Only that date, and sorted by start time.

Test design

Black-box and white-box testing

Black-box (specification-based)

  • Designed from requirements and criteria
  • No knowledge of the code needed
  • Equivalence partitions, boundary values, decision tables, state transitions
  • Finds missing and misunderstood behaviour

White-box (structure-based)

  • Designed from the code itself
  • Aims to exercise statements and branches
  • Measured with code coverage
  • Finds untested paths and dead code

Start black-box from the acceptance criteria, then use coverage to see what you missed.

Test design

Boundary value analysis

Bugs live at the edges

Edges are everywhere

19

Test design

What makes a good test case

1

Specific

Exact input data and steps, not "enter some events"

2

One expected result

Observable and unambiguous: what you should see

3

Independent

Sets up its own data; does not depend on another case

4

Traceable

Linked to a story and an acceptance criterion

5

Designed, not guessed

Chosen from partitions, boundaries, tables, states

6

Includes the unhappy path

Errors, empty states, no permission, no network

Test that it fails correctly, not only that it works. Most real users hit an error path within their first minute.

Test design

Code coverage: a useful flashlight, a poor target

src/events/label.js

function label(event) {
  let text = event.title;
  if (event.cancelled) {
    text += ' (cancelled)';
  }
  return text;
}

// One test: label({ title: "Parade", cancelled: true })
// Statement coverage: 100%  ·  Branch coverage: 50%

Statement coverage

Every line ran at least once.

Branch coverage

Every decision went both ways. Here, the not-cancelled path never ran.

Use it to find gaps

Low coverage shows untested code. High coverage proves little.

Tests need assertions

Code that runs without any expect() is "covered" but untested.

Defects

The defect life cycle

1

New

Reported with steps

2

Triaged

Severity, priority, owner

3

In progress

Branch and failing test

4

Fixed

Pull request merged

5

Verified

Reporter retests

6

Closed

Test stays in the suite

Reopened if verification fails. Rejected if it cannot be reproduced, is a duplicate, or works as designed, always with a reason.

Someone else verifies

The person who reported it, or a teammate. Not only the person who fixed it.

Use the board

Labels or columns on GitHub Projects track the states. No separate tool needed.

Test plan

Your test plan, in six parts

1

Scope

Which stories and NFRs are tested this sprint; what is explicitly out of scope.

2

Approach

Levels and techniques: unit and integration in CI, system tests on phones, one usability round.

3

Environment

Test database and seed data, browsers and devices, the deployed test URL.

4

Entry and exit criteria

When testing starts (story merged) and stops (all P1 fixed, criteria pass).

5

Roles and schedule

Who designs, runs, and verifies; when each round happens in Sprint 2.

6

Risks

Riskiest areas from the register get the most tests: dates, permissions, offline.

ISO/IEC/IEEE 29119-3:2021, Software testing: Test documentation

26

Test plan

When to start testing, and when to stop

Entry: ready to test when

  • The story is merged to main and deployed to the test URL
  • Its acceptance criteria are written and agreed
  • Seed data and test accounts exist
  • CI is green

Exit: done testing when

  • Every acceptance criterion has a passing test case
  • No open Critical or P1 defects
  • Top NFRs measured and recorded
  • Known minor defects listed in the release notes

Put the exit criteria in your Definition of Done. Then "done" means tested, not just coded.
