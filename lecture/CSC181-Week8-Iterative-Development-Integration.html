Iterative development

Iterative and incremental

Definition

Build the system in small, working increments, and revisit each part as you learn, instead of building every part once, in order.

1

Incremental

Add a new working piece each cycle: one more story done end to end

2

Iterative

Improve what exists: rework, refine, and fix based on feedback

3

Together

Every sprint ends with software someone can use and react to

A half-built feature is worth nothing to a user. Three finished stories beat eight that are 80% done.

C. Larman & V. Basili, "Iterative and Incremental Development: A Brief History", IEEE Computer (2003)

05

Iterative development

Build vertical slices, not horizontal layers

Horizontal: layer by layer

  • Week 1: the whole database
  • Week 2: the whole API
  • Week 3: all the screens
  • Nothing works until the end
  • Integration problems arrive last, all at once

Vertical: story by story

  • Slice 1: today's events, list only
  • Through every layer: screen, API, database
  • Deployed and usable after a few days
  • Each slice adds one story
  • Integration problems arrive early, one at a time

Walking skeleton: the thinnest slice that runs end to end and is deployed. Build it first, then add flesh to it.

A. Cockburn, Crystal Clear: A Human-Powered Methodology for Small Teams (2004)

Task planning

What makes a good task

1

Small

Done in a day or less. Bigger means it hides unknowns.

2

Owned

One name on it. "The team" owns nothing.

3

Clear finish

Anyone can tell when it is done.

4

Testable

Includes or pairs with its tests.

5

Linked

Belongs to a story; the story belongs to the goal.

6

Visible

On the board from the start, not added after the fact.

If a task has sat in "In progress" for three days, it is too big or it is blocked. Split it or ask for help at the next stand-up.

Task planning

Sizing work without false precision

Relative sizing

Compare stories with each other, not with the clock: "Is this bigger than the event list?"

T-shirt sizes (S, M, L) or story points (1, 2, 3, 5, 8) both work.

Planning poker

Everyone shows a size at the same time. The highest and lowest explain why, then vote again.

The discussion finds hidden work; the number matters less.

Hours for tasks

Tasks are small enough to guess in hours: 1, 2, 4, or 8.

Compare the guess with reality in your log. That is how estimates improve.

Velocity is what the team actually finished last sprint. Use it to plan Sprint 2, not to compare teams.

M. Cohn, Agile Estimating and Planning (2005)

Issue tracking

Anatomy of a useful issue

Event times show 0:00 PM at noon #27

openbugsprint-1assigned to Ben

Steps: open the event list on Oct 20; look at "Opening parade" (12:00).

Expected: 12:00 PM. Actual: 0:00 PM.

Where: Chrome on Android, main at commit 4f2a9c1.

Notes: likely in formatTime; see screenshot.

Linked: branch 27-fix-noon-time · pull request #31 · Closes #27

A title that says what

Someone scanning the board knows the problem without opening it.

Reproducible

Steps, expected, actual, where. A bug no one can reproduce cannot be fixed.

Labelled and assigned

Type (story, task, bug), sprint, and one owner.

Linked to the code

Branch and pull request mention the number, so it closes itself.

Issue tracking

Is the sprint on track? Read the burndown

Above the line

Behind plan. Cut scope early, not on the last day.

Flat stretches

Nothing finished. Blocked, too-big tasks, or a stale board.

At the end

Unfinished stories go back to the backlog. Never "90% done".

Integration

Continuous integration

Definition

Team members merge their work into main frequently, at least daily, and each merge is verified by an automated build and tests.

1

Merge small and often

Hours or a day of work per pull request, not weeks

2

Automate the checks

Lint, build, and tests run on every push and PR

3

Fix a red build first

A broken main blocks everyone; it is the top priority

Integration pain grows with the time between merges. If it hurts, do it more often.

M. Fowler, "Continuous Integration" (2006), martinfowler.com

15

Integration

A CI workflow in one file

.github/workflows/ci.yml

name: CI
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci          # install exactly
      - run: npm run lint    # style and errors
      - run: npm test        # unit tests
      - run: npm run build   # it compiles

Runs on every push

A fresh machine, so "works on my laptop" is tested for real.

Blocks bad merges

With branch protection, the merge button waits for green.

Use your stack

Python, PHP, or Java work the same way: install, lint, test, build.

Keep it fast

Under five minutes, or people stop waiting for it.

Running the Sprint 1 review

1

Sprint goal

Read it aloud. Was it met? Yes, partly, or no, in one sentence.

2

Live demo

Show the deployed prototype doing real stories. Not slides, not a video.

3

Done and not done

Which stories meet the Definition of Done; which go back to the backlog.

4

Board and burndown

Show the board as it is now. Explain any flat stretches honestly.

5

Feedback

Questions from the instructor and classmates. Write them down as issues.

6

Next

What changes in the backlog for Sprint 2 because of today.

K. Schwaber & J. Sutherland, The Scrum Guide (2020)

19

Sprint review

What counts as a working prototype

It is

  • Deployed at a URL, or runs from a fresh clone with the README
  • At least one story works end to end, through every layer
  • Uses real data paths, even with sample data
  • Merged on main, with CI green
  • Honest about what is missing

It is not

  • Screenshots or a Figma prototype
  • Code that runs only on one laptop
  • Features demoed from unmerged branches
  • Hard-coded screens with no back end
  • "It worked yesterday"

Smaller and real beats bigger and fake. One working story is a better Sprint 1 than five mock-ups.
