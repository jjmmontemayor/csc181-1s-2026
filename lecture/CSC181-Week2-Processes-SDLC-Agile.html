03

Software process

What a software process is

Definition

A structured set of activities, with their inputs, outputs, roles, and constraints, used to develop and evolve a software system.

Specification

What should the system do, and under what constraints?

Design & implementation

How will we structure and build it?

Validation

Does it do what users actually need?

Evolution

How will it change as needs change?

Fundamental activities: I. Sommerville, Software Engineering, 10th ed. (2015), Ch. 2 · SWEBOK v4

04

Software process

Why processes matter

Coordination

Many people, one product. Who does what, and when?

Predictability

Stakeholders want to know what they get, and when.

Quality

Reviews, tests and checkpoints are built into the flow.

Visibility

Progress can be seen, measured and discussed.

Learning

A defined process can be inspected and improved.

Accountability

Work and decisions leave a trail: issues, commits, reviews.

A process is a tool, not a ritual. Following steps without knowing why they exist is cargo-cult process.

Software process

A process description has four parts

Activities

What is done: write requirements, review code

Artifacts

What is produced: backlog, design, test report

Roles

Who is responsible: product owner, developer, tester

Conditions

What must be true before and after an activity

Example condition: a pull request is merged only after one approving review and passing tests.

In your team project: GitHub issues (activities), repository files (artifacts), team roles, and merge rules (conditions).

Software development life cycle

Maintenance is most of the life cycle

Corrective

Fix defects found after release

Adaptive

Adjust to a changed environment: new OS, new API

Perfective

Improve features or performance

Preventive

Refactor to avoid future problems

Software is rarely "done". It evolves as users, laws, devices and platforms change.

Implication: code is read and changed far more often than it is written. Readability, documentation and tests pay off long after launch.

Process models

Two broad families

Plan-driven

  • Activities planned in advance
  • Progress measured against the plan
  • Heavy upfront requirements and design
  • Examples: Waterfall, V-Model

Iterative / incremental

  • Plan, build and review in short cycles
  • Progress measured by working software
  • Requirements evolve with feedback
  • Examples: Incremental, Spiral, Agile

Most real projects are hybrids that mix elements of both families.

CSC181 · Week 2 · Software processes, SDLC, and agile

11

Process models · example

Waterfall in practice: an ATM cash-withdrawal system

1

Requirements

A signed-off document, frozen before design: withdraw up to ₱20,000 a day, keep the card after 3 wrong PINs, reply within 5 seconds.

2

Design

Full specifications: card reader, PIN pad, cash dispenser, transaction service, and the database for accounts and daily totals.

3

Implementation

Programmers code every module, such as computeNotes(amount), which picks the bills. No user sees the system yet.

4

Testing

Only after all coding is done does QA test the whole system, end to end, against the requirements document.

5

Operation & maintenance

ATMs are installed in branches; later patches handle new card standards and new regulations.

The catch: during testing, the bank asks for ₱200 bills. That change goes back through design and implementation, the most expensive point to find it.

Process models · example

V-Model in practice: the same ATM

LevelDesign side (left)Matching test (right)
Requirements ⟷ AcceptanceCustomers can withdraw up to ₱20,000 a dayBank staff and pilot customers use a trial ATM in a branch and confirm the daily limit on real accounts
System design ⟷ System testATM talks to the bank server, replies within 5 s, keeps the card after 3 wrong PINsWhole ATM and server in a test lab: 3 wrong PINs keeps the card; response time measured under load
Architecture ⟷ IntegrationCard reader, PIN pad, dispenser, transaction service, network linkTransaction service with the dispenser: ₱2,500 approved means exactly ₱2,500 out; a network drop mid-transaction does not debit the account
Module design ⟷ Unit testcomputeNotes(amount) picks which bills to dispensecomputeNotes(2500) returns 2 × ₱1,000 + 1 × ₱500; computeNotes(2550) is rejected

The difference from waterfall: each test plan is written during its design stage, before any code exists. Coding sits at the bottom of the V.

14

Process models

Incremental development

Outline requirements

1

Increment 1

Core features

2

Increment 2

More features

3

Increment 3

And so on

User feedback on each increment shapes the next one.

Benefits

Users get value early and give feedback. Changing requirements costs less than in waterfall.

Risk: the structure degrades

Each increment is built to fit the new feature, not the whole system. Without refactoring (cleaning up the design as you go), shortcuts pile up as technical debt. Diyandi app: the vendor and venue lists copy the event-list code; a time-format bug now needs the same fix in three places.

Risk: progress is harder to see

There is no complete upfront plan to measure "% done" against, and docs fall behind the code. Managers can't track progress and new members can't see how parts fit. Fix: keep the backlog, release notes and architecture notes current.

Process models

Iterative vs. incremental

Incremental

Build the product piece by piece. Each piece is mostly finished when delivered.

Like painting one section of a mural at a time.

Iterative

Build a rough version of the whole, then refine it repeatedly.

Like sketching the whole mural, then adding detail over several passes.

Agile combines both: each iteration delivers an increment, and the product is refined through feedback.

16

Process models

Spiral model: one loop per major risk

1

Objectives

Goals, alternatives, constraints

2

Risks

Identify and resolve, often by prototyping

3

Develop

Build and verify the next level

4

Plan

Review and plan the next loop

Each loop repeats the four steps, at growing cost and detail.

Good for

Large, high-risk or novel systems.

Makes risk explicit

You will build a risk register in Week 5.

Watch out

Needs risk-assessment expertise; costly for small projects.

Boehm, "A Spiral Model of Software Development and Enhancement" (1988)

17

Process models · example

Spiral in practice: a Diyandi emergency-alert system

Goal: warn up to 100,000 festival attendees within one minute of an emergency, such as a fire, a crowd crush or a storm.

LoopBiggest riskHow the loop reduced itDecision
1Can we reach everyone within a minute?Load test with the telco's SMS gatewaySMS alone is too slow: use push notifications, with SMS as fallback
2Will attendees install an app?Mock-up shown to 20 festival-goersMost won't: add SMS opt-in by texting a keyword
3What about false alarms?Approval step designed with organizers; core system built and verifiedTwo people must confirm before an alert is sent
4Does it work in real crowds?Pilot at one event before the full festivalFix the issues found, then roll out festival-wide

The payoff: the riskiest unknowns are tackled first, while they are still cheap. If loop 1 had shown alerts were impossible, the project could stop before most of the budget was spent.

18

Process models

Prototyping: build to learn

Throwaway prototype

  • Answers one question, such as "Can users find today's events?"
  • Discarded after it teaches you something
  • Wireframes are throwaway prototypes

Evolutionary prototype

  • Refined step by step until it becomes the product
  • Needs real engineering quality from the start

Useful when

Requirements are unclear, the UI is central, or a technical approach is unproven.

Watch out for

Stakeholders mistaking a prototype for a finished product; "quick and dirty" code becoming permanent.

Agile values

The Agile Manifesto: four values

"We are uncovering better ways of developing software by doing it and helping others do it. Through this work we have come to value:"

Individuals and interactions

over processes and tools

Working software

over comprehensive documentation

Customer collaboration

over contract negotiation

Responding to change

over following a plan

"That is, while there is value in the items on the right, we value the items on the left more."

Beck et al., Manifesto for Agile Software Development (2001), agilemanifesto.org

22

Agile values

Common misreadings

MisreadingWhat the manifesto actually says
"Agile means no documentation."Documentation has value; working software is valued more.
"Agile means no planning."Plans exist; they are revised as we learn.
"Agile means no process."Processes and tools matter; people and interaction matter more.
"The customer can change anything at any time."Change is welcome, but it is managed through the backlog and iterations.

Agile values

Selected agile principles

Early and continuous delivery

Our highest priority is to satisfy the customer through early and continuous delivery of valuable software.

Welcome change

Welcome changing requirements, even late in development.

Deliver frequently

From a couple of weeks to a couple of months, preferring the shorter timescale.

Work together daily

Business people and developers work together daily throughout the project.

Working software

Working software is the primary measure of progress.

Simplicity

Maximize the amount of work not done.

Reflect and adjust: at regular intervals, the team reflects on how to become more effective, then tunes its behavior.

6 of the 12 principles behind the Agile Manifesto · agilemanifesto.org/principles.html

26

Scrum

Three accountabilities, one Scrum team

Product Owner

  • Maximizes the value of the product
  • Owns and orders the product backlog
  • Represents stakeholders
  • One person, not a committee

Scrum Master

  • Coaches the team in Scrum
  • Removes impediments
  • Facilitates events
  • A servant-leader, not a boss

Developers

  • Everyone who builds the increment: code, design, tests, docs
  • Plan the sprint backlog
  • Self-managing: decide how to do the work

The 2020 Scrum Guide calls these accountabilities within one team, typically 10 people or fewer.

Schwaber & Sutherland, The Scrum Guide (2020)

Scrum vs. Kanban

ScrumKanban
RhythmFixed sprints, 1–4 weeksContinuous flow, no sprints
RolesProduct Owner, Scrum Master, DevelopersNone required; existing roles stay
PlanningCommit to a sprint goal at sprint planningPull the next item when there is capacity
Limits work byWhat fits in the sprintWIP limits per board column

QuestionLeans plan-drivenLeans agile

Team milestone · this week

Form your team and pick a preliminary domain

Suggested roles

  • Product Owner: keeps the backlog ordered; speaks for users
  • Scrum Master / Facilitator: runs meetings, tracks blockers, keeps records
