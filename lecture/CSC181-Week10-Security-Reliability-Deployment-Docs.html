Secure coding

Security is a property of the whole system

C

Confidentiality

Only the right people see the data: organizer phone numbers stay private

I

Integrity

Only the right people change the data: visitors cannot edit the schedule

A

Availability

It works when needed: the schedule loads on festival night

Least privilege

Every user, service, and key gets only the access it needs.

Defence in depth

Hiding a button is not security. Check again on the server.

Secure by default

New accounts, settings, and endpoints start locked, not open.

06

Secure coding · example

Injection: never build queries from strings

Before: string concatenation

const rows = await db.query(
  "SELECT * FROM events WHERE title LIKE '%"
  + q + "%'"
);

// q = "x' OR '1'='1"
// every row comes back, or worse

After: a parameterized query

const rows = await db.query(
  'SELECT * FROM events WHERE title LIKE $1',
  ['%' + q + '%']
);

// the database treats q as data,
// never as part of the command

Same idea for HTML

Let the framework escape output. Avoid innerHTML with user text (cross-site scripting).

Validate input too

Length, type, and format on the server. But validation does not replace parameters.

Secure coding · example

Access control belongs on the server

src/api/auth.js · src/api/events.js

export function requireOrganizer(req, res, next) {
  if (!req.user) return res.status(401).end();
  if (req.user.role !== 'organizer')
    return res.status(403).end();
  next();
}

router.put('/events/:id', requireOrganizer, async (req, res) => {
  const event = await Events.find(req.params.id);
  if (event.ownerId !== req.user.id)
    return res.status(403).end();
  // ...validate and save
});

Who are you?

Authentication: 401 if not signed in.

What may you do?

Authorization by role: 403 for visitors.

Is it yours?

Ownership check: organizers edit only their own events.

Test it

Integration tests for 401 and 403, as in Week 9 (defect #34).

Secure coding

Secrets, passwords, and dependencies

Secrets

  • Never commit keys or passwords; use .env
  • .env in .gitignore; .env.example lists names
  • Leaked once? Rotate it. Deleting the commit is not enough
  • Turn on GitHub secret scanning

Passwords

  • Use the framework's auth if you can
  • Otherwise hash with bcrypt or Argon2
  • Never plain text, MD5, or SHA-1
  • Rate-limit login; allow long passphrases

Dependencies

  • Commit the lockfile
  • Run npm audit or pip-audit in CI
  • Enable Dependabot alerts
  • Fewer packages, from known maintainers

Git remembers everything. A key committed in Week 7 and deleted in Week 8 is still in the history, and bots scan public repositories within minutes.

OWASP Cheat Sheet Series: Password Storage · NIST SP 800-63B

Reliability

Reliability: what happens when things go wrong

Definition

The ability of a system to perform its functions under stated conditions for a specified time, including when parts of it fail.

1

Availability

The share of time it is up. 99% still means about 7 hours down a month.

2

Fault tolerance

One part fails; the rest keeps working, perhaps with less.

3

Recoverability

How fast you are back, and how much data you lose.

Assume the network, the server, and the user will all fail sometimes. Decide in advance what the user sees.

ISO/IEC 25010:2023, Product quality model

Reliability

Fail gracefully

When this failsThe user seesThe system does
Network drops"Showing schedule from 7:42 PM. Reconnecting…"Serves the cached schedule; retries in the background
API is slowA loading state, then a clear message after 10 sTimes out; does not hang forever
Invalid input"Start time must be before end time" next to the fieldValidates on the server, not only the form
Server error"Something went wrong. Your changes were not saved."Logs the details with a request ID; no stack trace to the user
Save conflict"Ben edited this event a minute ago. Review his change?"Checks a version number before saving

An error message should say what happened and what to do next, in the user's language, without blaming them.

Reliability

Logs and monitoring: know before your users tell you

One structured log line

{
  "time": "2026-11-02T19:04:11+08:00",
  "level": "error",
  "msg": "event update failed",
  "eventId": 12,
  "userId": "u_83",
  "requestId": "r-7f3a",
  "error": "timeout after 5000 ms"
}

// no email, password, phone, or token

Structured

JSON fields you can search and filter, not free text.

Useful

Enough to find the cause: what, where, which request.

Safe

No passwords, tokens, or personal data. Logs leak too.

Watched

A free uptime check and error alerts to the team chat.

13

Reliability

Backups you have actually restored

Back up

The database, uploaded files, and configuration.

Automatically, on a schedule, to a different place than the server.

Restore

A backup you have never restored is a hope, not a backup.

Practise once: restore into a test database and check the data.

Migrate safely

Schema changes as migrations in the repository.

Back up before running them in production.

Two questions for your plan: how much data can we lose (an hour? a day?), and how long can we be down?

Deployment readiness

Environments: never test on the real thing

Local

Your laptop; sample data

CI

Fresh machine; runs the tests

Staging

Same setup as production; test data

Production

Real users and real data

Same code everywhere

Only configuration changes between environments. Never edit code on the server.

Staging catches surprises

Missing variables, slow queries, mobile layout, HTTPS issues.

Production is protected

Deployed only from main, by the pipeline, after tests pass.

Deployment readiness

A deployment-readiness checklist

Build and deploy

  • Deploys from main by the pipeline
  • CI green; tests cover key journeys
  • Staging tested before production
  • Rollback tried once
  • Release tagged with notes

Security and privacy

  • No secrets in the repository or history
  • DEBUG off; generic error pages
  • Access checked on every endpoint
  • npm audit clean or explained
  • Privacy notice and delete option live

Operate and support

  • HTTPS on the public URL
  • Logs without personal data
  • Uptime check and error alerts
  • Daily backup; one restore practised
  • README and user guide current

Individual work: adapt this or the security and privacy list to your project; mark each item done, not done, or not applicable, with evidence.

Maintenance

Most of a system’s life is maintenance

1

Corrective

Fix defects found in use. "Noon shows as 0:00 PM."

2

Adaptive

Keep up with a changing world: new phone OS, new map API terms.

3

Perfective

Improve or add: a vendor directory next year, faster loading.

4

Preventive

Reduce future problems: update packages, refactor, add tests.

Studies commonly put maintenance at well over half of lifetime cost. Every decision this semester is also a decision for the people who maintain it.

ISO/IEC/IEEE 14764:2022, Software maintenance · B. Lientz & E. B. Swanson (1980)

24

Maintenance

Technical debt: borrow on purpose, and pay it back

What it is

Shortcuts that save time now and cost time later, like interest on a loan.

Duplicated code, missing tests, hard-coded values, outdated packages.

Deliberate and prudent

"We ship the demo with a hard-coded venue list and replace it in Sprint 3."

Fine, if it is written down.

Reckless

"No time for tests." "We will fix it later" with no issue.

The interest grows until no one dares change anything.

Make debt visible: a "tech-debt" label on issues, a line in the release notes, and some time in every sprint to pay it down.

W. Cunningham, OOPSLA experience report (1992) · M. Fowler, "TechnicalDebtQuadrant" (2009)

Ready to ship?

3 min

Teams of 3 or 4. Pick a system on the right. Each has hidden problems.

7 min

5 min

5 min

Share: one team per system reads its top problem; others add what they missed.
